# IDC 财务系统开发路线与实现注意事项

> 技术栈建议：Go + Vue 3 + TypeScript + PostgreSQL + Redis  
> 目标：高性能、易维护、易扩展、安全、支持主题/扩展包、兼容魔方财务、提供完整 API，并支持魔方财务数据库迁移。

---

# 1. 项目目标

本项目不是简单重写一个财务面板，而是设计为一个可长期维护的 IDC Billing Core。

核心目标：

- 高性能、低资源占用
- 前后端分离
- 支持主题自定义
- 支持第三方扩展包
- 支持魔方财务作为上游
- 支持魔方财务作为下游
- 提供大量公开 API
- 支持 API Token 权限控制
- 防 SQL 注入、XSS、CSRF、SSRF、越权等常见漏洞
- 加强用户数据、财务数据和密钥保护
- 支持魔方财务数据库导入
- 保证财务流水可追踪、可审计
- 支持异步任务和队列
- 后续可以扩展 Proxmox、Virtualizor、VMware 等 Provider

# 6. 财务设计注意事项

---

## 6.1 禁止使用 Float 保存金额

禁止：

```go
float64
```

不要：

```text
0.1 + 0.2
```

使用：

```text
Decimal
```

或者最小货币单位整数。

例如：

```text
100.25 CNY

存：

10025
```

复杂计价使用：

```sql
NUMERIC(20, 8)
```

---

# 6.2 钱包必须有流水

不能只有：

```text
users.balance
```

必须有：

```text
wallet_accounts
wallet_transactions
```

示例：

```text
wallet_transactions

id
account_id
type
amount
balance_before
balance_after
currency

reference_type
reference_id

description
created_at
```

---

## 6.3 财务流水禁止直接修改

不要提供：

```text
修改流水
删除流水
```

应该使用：

```text
冲正交易
```

例如：

```text
原记录：

-100

错误纠正：

+100
```

这样完整保留历史。

---

# 6.4 财务操作必须使用数据库事务

例如：

```text
扣款
创建流水
更新订单
续费服务
```

必须在同一个事务中完成关键数据库操作。

逻辑：

```text
BEGIN

锁定账户

检查余额

扣除余额

创建交易流水

更新订单

COMMIT
```

任何一步失败：

```text
ROLLBACK
```

---

# 6.5 高并发扣款必须防止重复消费

不要：

```text
读取余额
↓
代码判断
↓
UPDATE
```

因为多个请求可能同时读取旧余额。

推荐：

- 行锁
- 乐观锁
- 原子 UPDATE
- 数据库事务

例如：

```sql
UPDATE wallet_accounts
SET balance = balance - $1
WHERE id = $2
AND balance >= $1;
```

然后检查：

```text
RowsAffected
```

# 7. 密码安全

推荐：

```text

```

禁止：

```text

```

```text

```


# 8. Session / Token

后台和客户端可以使用：

```text
HttpOnly Secure Cookie Session
```

第三方 API：

```text
API Key + Secret
```

可选：

```text
JWT + Refresh Token
```

如果使用 JWT：

- Access Token 短有效期
- Refresh Token 单独管理
- 支持主动注销
- 支持设备管理
- 支持 Token Revoke

# 10. 特别注意 IDOR 越权

这是 IDC 财务很容易出现的问题。

例如：

```http
GET /api/v1/services/1001
```

不能只判断：

```text
用户登录了吗
```

还必须检查：

```text
service.user_id == 当前用户ID
```

除非当前用户具有：

```text
service.read.all
```

权限。

所有资源都要做对象级授权：

```text
订单
账单
服务
工单
附件
API Token
```

# 第十五阶段：安全体系

安全不是开发完再补。

必须从第一天设计。

---

# 38. SQL 注入

禁止：

```go
fmt.Sprintf("SELECT * FROM users WHERE id=%s", id)
```

禁止：

```go
"SELECT * FROM users WHERE id=" + id
```

必须：

```sql
WHERE id = $1
```

sqlc：

```go
user, err := queries.GetUser(ctx, id)
```

---

# 39. 动态字段白名单

例如排序：

```text
sort=
```

不能直接：

```text
ORDER BY ${sort}
```

必须：

```go
switch sort {
case "id":
case "created_at":
case "price":
default:
    sort = "created_at"
}
```

---

# 40. XSS

用户输入：

```text
用户名
工单
备注
产品描述
公告
```

不能直接作为 HTML 输出。

建议：

- 默认 HTML Escape
- 富文本使用 Sanitizer
- CSP
- 禁止危险标签
- 禁止 javascript: URL

---

# 41. CSRF

Cookie Session 模式必须：

```text
CSRF Token
SameSite
Secure
HttpOnly
```

---

# 42. SSRF

IDC 系统非常容易出现 SSRF。

例如：

```text
Webhook URL
Provider URL
自定义 API
图片 URL
```

必须阻止访问：

```text
127.0.0.1

localhost

169.254.169.254

内网 IP

Unix Socket

file://

gopher://
```

如果业务允许访问内网 Provider，则必须通过：

```text
独立 Provider 白名单
```

而不是开放任意 URL。

---

# 43. 文件上传

需要：

- 扩展名检查
- MIME 检查
- 文件头检查
- 随机文件名
- 独立存储
- 不允许直接执行
- 图片重新编码
- 限制大小
- 限制数量
- 防路径穿越

---

# 44. Zip Slip

主题、扩展 ZIP 解压必须检查：

```text
../../
```

禁止文件写出目标目录。

---

# 45. 命令执行

核心业务不要：

```go
exec.Command("sh", "-c", userInput)
```

所有调用系统命令的参数必须严格白名单。

尽量不用 shell。

# 71. 开发时必须遵守的原则

## 原则 1

业务逻辑禁止写 Controller 里。

错误：

```text
Controller

里面：

SQL
支付
余额
邮件
Provider
```

正确：

```text
Controller

↓

Service

↓

Repository
```

---

## 原则 2

Provider 不允许直接操作财务核心。

Provider：

```text
负责资源
```

Core：

```text
负责账务
```

---

## 原则 3

Extension 不直接访问数据库。

应该：

```text
Extension

↓

Extension API

↓

Core Service
```

---

## 原则 4

前端永远不能成为安全边界。

所有权限：

```text
后端重新判断
```

---

## 原则 5

任何用户输入都不可信。

包括：

```text
Header

Cookie

JSON

Query

Path

文件

Webhook

Provider 返回值
```

---

## 原则 6

任何财务操作必须：

```text
可追踪

可审计

可恢复
```

---

## 原则 7

任何外部 API 调用都可能：

```text
超时

失败

重复

返回异常数据
```

因此必须：

```text
Timeout

Retry

Backoff

Circuit Breaker

Idempotency
```

---

# 72. 外部 Provider 调用建议

每次调用设置：

```text
Connect Timeout

Read Timeout

Total Timeout
```

不要无限等待。

---

# 73. Retry

不是所有请求都能 Retry。

例如：

```text

```

通常可以。

但：

```text
CreateServer
```

不能盲目 Retry。

必须有：

```text
Request ID

Idempotency
```

否则可能创建两台服务器。


```text
2
```

# 87. 开发原则总结

整个项目始终遵守：

```text
Core 保持稳定

Provider 负责资源

Compatibility 负责兼容

Theme 负责界面

Extension 负责扩展

API 负责连接外部

Worker 负责耗时任务

PostgreSQL 负责真实业务数据

Redis 负责临时数据和异步任务
```

最终目标：

```text
即使删除 MagicCube Adapter

核心系统依旧完整运行。

即使更换主题

业务代码不发生变化。

即使新增 Provider

订单和财务核心不需要修改。

即使增加 Extension

不需要修改核心源码。
```

这才是这个 IDC 财务系统后期容易维护、容易开发、容易扩展的关键。
